## 1. 起点：v0.1.0 原本要做的事（09-03 深夜 ~ 09-04）

**证据**：仓库最早痕迹是 `.mimosa/history` 里 `2026-09-03T16:45Z`（= 09-04 00:45）的安全扫描；首个提交 `fa3cde1`（09-04 17:44）一次性提交 69 个文件；随仓库一起提交的设计文档是 `Smart Transition Engine 实现任务.md`（1568 行，37 章）。

**当时的需求（原始任务书目录）**：项目背景 → 核心设计思想 → 主动切歌 vs 自然播放两种场景 → 不要在播放中做重型分析 → 不用 AI → TrackAnalysis 数据结构 → BPM/Beat/Energy/Spectral/Vocal 分析 → 切出点/切入点/候选点匹配 → Transition Score（Phrase/Beat/Vocal/Energy 四个分项）→ Transition Duration → 过渡类型自动选择 → EQ Transition → Crossfade 曲线 → 缓存 → 性能 → Fallback → 验收标准。

**当时的实现落点**（`fa3cde1` 提交信息原文）：

- 后端 FastAPI + SQLite + numpy：B 站分享链接解析（b23.tv 短链/收藏夹）→ **音频与封面下载入库（分段并发）**；
- WBI 签名 + buvid 指纹防风控；扫码登录；导出为真实收藏夹链接；
- 流式播放 API（HTTP Range）；TrackAnalysis 分析缓存（BPM/节拍/能量/人声代理）；
- 前端 Jinja2 + htmx + 原生 JS，**零构建**：曲库 / 队列面板 / 播放条 / Media Session 锁屏控制；
- **Smart Transition：Web Audio 双轨 Equal-Power 交叉淡化**；播放顺序 = 按过渡得分贪心排序的自动决策链；
- 测试：pytest 28（WBI 黄金向量 / URL 安全 / 链接解析 / 分段下载 / DSP 分析）+ node 11（过渡打分 / 规划 / 策略）。

**这一版的隐含前提**：音乐会**下载到本地**，所以能离线分析音频；播放的是本地文件。

## 2. 分水岭：v0.2.x（09-05 ~ 09-06）——两件事同时发生

### 2.1 需求变更 ①：前端要重做（用户原话）

09-05 凌晨 04:56，用户在 Claude Code 里贴了三张截图，原话：

> 「了解项目，重新生成一个前端。」（`/design`，附三张参考图）
>
> 09-05 05:39 再开一单：「了解这个项目。然后设计一个前端原型给我……这是一个 bilibili music 项目，要求你可以参考 spotify，apple music，youtube music 等界面。」
>
> 之后在另一个会话里继续：「重新设计一个前端，前端技术要求为**方便打包，响应式布局**。」

**怎么实现的**：

1. 09-05 13:03 `8a318b5` 落了一版 v3 前端原型（Spotify × Apple Music 混合设计，桌面 + 手机可交互）——在 `/design` 目录里裸做静态原型，不动已有代码；
2. 随后一整天（`5891568` 到 `ff80c47` 等，09-05 一天共 50 个提交）是**用户逐条看、逐条提意见的密集迭代**：移除侧栏导航、隐藏任务浮片、搜索栏改纯搜索、最近收藏实时刷新、取消播放胶囊进度条、隐藏横滑架滚动条、主页改放线上推荐歌单、封面改真实拼贴、手机搜索改底部圆钮……
3. 其中**光「侧栏毛玻璃」就来回改了 12 个提交**（`c6d26d3` → `eefd8ae`，09-05 21:47 ~ 09-06 00:01）：加模糊 → 提不透明度 → Apple 配方 → 高不透明雾面 → 关掉 → 全透明 → 纯 `filter: blur(30px)` 镜像层 → Uiverse 配方 → 消除渐变不均匀。这条线最终以「**镜像模糊层**（对侧栏背后内容做模糊，不依赖 `backdrop-filter`）」收口，原因见技术复盘。

### 2.2 需求变更 ②（没人明说，但影响最大）：从「下载入库」改成「纯在线流式」

**证据**：v0.1.0 的 `/api/stream` 走的是 `files.audio_response(Path(song.audio_path))`——**播放本地文件**；09-05 `0a86941` 新增了代理 B 站 CDN 的实时流路由（`upstream.aiter_bytes(64*1024)`）；09-07 `c2b4e30` 把 `audioUrl` 全面切到 `/api/stream/{s.bvid}` 并标注「纯在线：实时流代理（支持 Range）」——至此播放不再依赖本地文件。

**为什么改**（推断 + 现场证据）：v0.1.0 的「下载入库」有硬伤——占磁盘、导入慢、B 站音频有防盗链时效、多设备各存一份；而目标场景（用户贴着手机/电脑听歌）用流式代理更合适。

**代价（被明确保留的技术债）**：

- **Smart Transition 直接停用**。`app/web/static/app.js` 里留着 `function smartEnabled() { return false; }` 和一句注释：「**Smart Transition：纯在线版已停用（依赖本地音频分析）**；保留调用点与降级路径，代码可整体回退」。
- `app/analysis/`（BPM/节拍/能量/人声分析）整目录变成死代码，`POST /api/songs/analysis` 路由缺失（后来被前端 PRD 记为 D-2 / G-5）。
- 换来的是：README 现在写「正常播放不保存整首音频」，并且启动迁移会把旧版本的本地音频转成在线记录后删掉文件。

> 这是整个项目**最大的一次需求变更**，且在 commit 里没有一封正式的「决策记录」，只能从代码注释和 PRD 的 D-2/G-5 反推。教训写在技术复盘里：**砍功能要写决议，不要只留死代码。**

### 2.3 09-06 ~ 09-07 前端继续长内容

`1f558df` UP 主个人界面初稿 → `8c9b04b` 歌手详情页 → `98789e8` 歌曲详情页补播放控制条 → `a002965` 修 UP 主页显示 bug → `c74e725` 首页丰富 → `c2b4e30` 大提交（账号隔离 + 在线流 + 播放重做）→ `7043a39` merge `feat/liquid-glass` → `2ea61ca` 清掉合并残留的错误 squircle 参数。

## 4. v0.4.0（09-09 03:03）：用户实测批次 + 合集容器

**提交**：`5a1c435`「B6 user-test batch + collection-container search (#23-#37)」。

**需求来源**：一批用户实测反馈（内部编号 #23-#37，注意这套编号和后来 `issue-ledger.md` 的 #23+ 不是一回事，容易混）。原文摘要：

> 「中文输入法搜索修复（合成期间不重渲染下拉、type=text）」

> 「逐分 P 星标收藏（空心 → 实心）；collected 标记 + 迁移；默认歌单 + 侧栏计数刷新」
> 「通知媒体卡完整元数据 + 点击打开；UP dock z-index；搜索封面尺寸；搜索返回栈」
> 「资料库 tab、收藏按钮对齐、去掉每行的专辑 badge」

**这一版真正的产品洞察**：**B 站有三种内容形态，必须统一成一套语义。**

| 形态       | B 站侧             | BiliMusic 侧                           |
| ---------- | ------------------ | -------------------------------------- |
| 单视频     | 一条收藏           | 一首歌                                 |
| 多 P 视频  | 一条收藏           | 一张「专辑」（paged），分 P 是曲目     |
| 跨视频系列 | 每个视频各一条收藏 | 一张「合集」（series），每个视频是曲目 |

v0.4.0 先做「多 P = 容器 + 逐分 P 星标」；「系列」留到 v0.5.0。

## 5. v0.5.0（09-09 17:03 ~ 18:51）：系列合集 + 同步一致性

**需求**：`docs/v0.5.0-prd.md`（09-09 17:03 `1c7cb95` 把旧的规划文档全删，换成一封 v0.5.0 PRD——**这是项目第一次有正式 PRD**）。

一句话目标（PRD 原文）：「让 B 站跨视频**系列**也能变成一个『合集容器』，点开看到所有作品、逐作品收藏；同时修复 v0.4.0 遗留的『同步时合集反复导入』一致性问题。」

**实现落点**（`d089328` 提交信息）：

- 同步一致性（P0 前置）：对账的「已在本地」判断改用全量行（`only_collected=False`），合集只有未收藏子作品时不再被反复导入；
- 系列链接解析：`collectiondetail?sid=` → `SeriesRef`（明链 / 分享文本 / `b23.tv` 短链重定向），`submit_any` 分发到系列导入；
- 数据模型：`Album kind="series"`、`source_bvid="sid:<id>"`，不加新列；曲目行 = 系列内每个视频，多 P 视频复用 paged 语义展开；
- 拉取导入：`seasons_archives_list` 分页 + **串行频控** + 进度按视频数；幂等断点续传、单视频失败降级；换设备重建时认领散曲（与收藏夹合并）；
- 收藏/删除语义：星标 = 该视频在 B 站收藏一次；移出/删单曲 = 取消该视频收藏 + 全部行退目录态；删容器 = 逐视频批量取消，失败登记 syncer 自愈重试且期间压制拉取（**不删完又被拉回**）；
- 测试：`tests/test_series.py`（14 例）+ `tests/test_sync_collected.py`（3 例）；pytest 137 passed。

**紧接着**（`60e95b7` 18:51）落地两个语义规则：「**曲库以 B 站收藏夹为准确数**」+「**打开即同步**」。

> 这两条是产品定位级的决定：BiliMusic 不是「另一个曲库」，而是 B 站收藏夹的一个**播放器前端镜像**。后面所有计数、删除、同步的设计都服从这条。

## 9. v1.3.0（09-10 16:29）：跨端播放会话（#23）

**需求**（09-09 提出，对标 Spotify Connect / YouTube Music 的多端体验）：

> 队列与播放进度只存在各自浏览器的 `localStorage.bmSession:<mid>` 里，设备之间互相不可见——手机上听到一半，走到电脑前只能从头开始。

**架构结论（关键）**：跨端接力转移的是**会话状态**，不是音频数据。接收端自己向后端取流并 seek 到目标位置即可——和 Spotify Connect 同原理。这决定了整个实现是「服务端 + SSE + 客户端 seek」，而不是任何形式的音频投送。

三个有利条件（台账原文）：音频由后端代理、任何设备可独立解析同一条流；SSE 事件总线按 mid 过滤、天然支持多订阅者；进程内任务单例已有成熟先例（`SyncState`）。

**三阶段落地**（同一天 16:00 ~ 16:18 四个提交）：

- **Phase 1**（`027b28e`）设备注册 + 服务端会话 + 只读展示 + 打开即续播；
- **Phase 2**（`d8b22c2` + `4efb497`）命令通道 + 移交握手 + 控制器态；远端遥控补齐 next/prev/seek（队列项带 duration，进度条可点即 seek）；
- **Phase 3**（`1881930`）立即预加载（点下去 **5ms** 就发起预加载）+ 交叉淡入淡出（接收端 350ms 淡入、发送端同窗口淡出）+ 修掉交接竞态。

**顺手修掉的两个真 bug**（都是端到端跑出来的）：

1. **交接竞态**：发送端在 350ms 淡出期间仍上报 `playing=true`，会把会话抢回去（实测接管成功后 active 又变回发送端）。修法：客户端一开始让出就按「已暂停」口径上报 + 服务端 `TAKEOVER_GRACE = 2.5s` 宽限窗。
2. **启动被登出**（BUG-022）：后端启动时到 B 站的请求抖动 → `accounts.activate()` 一次性失败 → 直接 reset 到未登录，必须重启才恢复。修法：网络类错误重试 2 次（1.5s/3s 退避），凭据失效（`BiliApiError`）不重试。

**范围收口**（`02de730`，用户拍板）：跨设备**采样级**相位对齐不做。用户原话：「几百毫秒相位差够了，用户体验差不多的」——由交叉淡入掩盖。

**发布 v1.3.0 后立刻炸了 CI**：Android job 的模拟器 smoke 测试等不到 `BILIMUSIC_WEB_READY`（BUG-023）。根因：Android 侧 Chaquopy 装的是 **pydantic 1.10.22**，开发 venv 是 2.x；新加的 `Field(default_factory=list, max_length=200)` 在 v1 上建模阶段直接抛错 → `app.api.routes` 导入失败 → 内嵌后端起不来。修复：去掉 v2-only 写法（`max_length`/`pattern` 改为运行时清洗）+ `model_dump()` 兼容 v1，并留下教训：「Android 侧是 pydantic 1.10，别用 v2-only 写法；改后端后先在本机构建 debug APK 跑一次 smoke，比等 CI 快。」

## 11. 跨阶段主线：需求到底变过几次

把 135 个提交按「需求主线」重排，会看到六条清晰的演变线。**这才是这个项目真正的骨架**，版本号只是它的刻度。

### 主线 1：曲库形态 —— 从「一首歌」到「三种内容形态的统一语义」

```
单视频 = 一首歌
  → v0.4.0：多 P 视频 = 专辑容器（paged），分 P 是曲目，逐分 P 星标
    → v0.5.0：跨视频系列 = 合集容器（series），每个视频是一条曲目
      → v1.0.x：计数口径统一到「视频级」，与 B 站收藏夹对齐
        → v1.2.0（BUG-020）：收藏粒度从 bvid 收到 bvid:cid（分集不再串台）
```

**难点不在功能，在语义**：同一个「收藏」动作，在三种形态下 B 站侧的语义完全不同（整视频收藏一次 / 分 P 各算一次 / 每视频各收藏一次）。台账 §2.4 的「B 站语义矩阵」就是为这个建的。这也是产品分析里那条「内容形态语义做对了」的由来。

### 主线 2：播放形态 —— 从「下载入库 + 智能过渡」到「纯在线流式」

```
v0.1.0：下载音频到本地 → 本地分析（BPM/节拍/人声）→ 双轨交叉淡化
  → 09-05：/api/stream/{bvid} 实时流代理（Range/206、不落盘）
    → 09-07：audioUrl 全面切到 /api/stream，Smart Transition 停用（smartEnabled() = false）
      → v1.2.0（BUG-021）：CDN 换源重试 + 前端停顿自愈 + Android 网络锁
```

**收益**：不占磁盘、导入即听、多设备零成本、绕开本地文件与 B 站防盗链的时效问题。
**代价**：智能过渡能力整体报废（`app/analysis/` 成为死代码），必须联网，音质受接口档位限制。

### 主线 3：产品定位 —— 从「单机播放器」到「多设备串流」

```
v0.1.0：一个网页，一个后端
  → v0.3.0：装上手机/桌面，多了原生能力（后台播放/通知/线控）
    → v1.3.0（#23）：服务端权威播放会话 + 设备间移交
      → v2.0.0（#26/#27/#29）：局域网自动发现 + 播放条即遥控器 + 手势串流
```

**这是最大的一次定位跃迁**：从「一个能听歌的网页」变成「同一账号多设备共享一份播放会话」。为此付出的代价见主线 4 与主线 6。

### 主线 4：登录 —— 从「短信 + 极验」到「二维码存相册 + 拉起 B 站 App」

```
v1.0.0：修 WebView UA + 第三方 Cookie 让极验能渲染（BUG-002）
  → 同日：captcha 接口重试 + 错误透出（BUG-003）
    → v1.0.1：整体下线短信登录，改成「点二维码 → 存相册 → 拉起 B 站 App 扫相册」（FEAT-001）
```

背后的判断：**极验是外部依赖，抗不过就不打，绕着走**。扫码在单手机上不方便（没法扫自己的屏幕），所以用「存相册 + 用 B 站 App 的相册入口扫」这个变通。

### 主线 5：真相源 —— 从「本地库」到「B 站收藏夹为准」

```
v0.1.0：入库即收藏（本地库 = 事实）
  → BUG-004：三处计数对不上（12 / 20+ / 13）
    → v0.5.0：曲库以 B 站收藏夹为准确数 + 打开即同步（本地 = 镜像）
```

这条决定了后面所有同步/删除/自愈逻辑的形态（失败后台对账、删除时压制拉取避免「删完又被拉回」）。

### 主线 6：交互 —— 从「设备整页」到「播放条即界面」

```
v1.3.0：设备/跨端能力放在播放队列面板的「设备」区
  → #26：升级成独立「设备」整页（桌面侧栏 + 手机底部 Tab）
    → 用户：「导航栏的设备这一栏，我觉得很不优雅，不要了」
      → v2.0.0：删整页；播放条本身既是状态显示又是遥控器；手机用手势（上拖/下拖），桌面用设备图标
```

**这是典型的「功能做对了，但入口做错了」**：串流本身没错，错在要求用户先「去设备页点连接」。最后的答案是把它降级成播放条的一个状态 + 一个手势。

## 15. 复盘：这套打法里什么值得保留，什么该改

### 值得保留

1. **台账（issue-ledger）+ 真 bug 记录（bugs.md）+ 验收手册（acceptance-manual）三件套**。
   - 台账管「新条目 + 状态 + 决策」，bugs.md 管「真机实测的现象→根因→修复→验证」，验收手册管「操作 → 期望」。
   - 关键设计：**台账只维护新增与状态，历史条目按来源索引不复制正文**——避免两处维护漂移。
2. **量测式验收**。不用「看起来没问题」，而是无头 Chrome + CDP 量 rect / computed style / `elementFromPoint`；e2e 用真触摸事件；用 `__toastLog` 断言「零提示」。这让 UI 类 bug 从「主观」变成「可回归」。
3. **先记不改**。用户说「先别动代码」的需求一律进台账并锁死，不夹带。
4. **方案对比再拍板**。#26 一次给出 5 个方案 + 工作量 + 优缺点，用户挑；比自己闷头实现再返工便宜得多。
5. **验证分层**：单测（pytest / node）→ 接口实测（真 cookie、真库）→ 页面实测（无头 Chrome）→ 端到端（多设备）。每层都能独立定位问题。

### 应该改

1. **重大变更没有 ADR（架构决策记录）**。砍掉 Smart Transition 这件事，只在 `app.js` 留了一句注释。半年后没人知道为什么。→ 建议 `docs/decisions/` 一页一条：背景 / 选项 / 结论 / 代价。
2. **死代码留得太多**。`app/analysis/` 整个目录、`smartEnabled()` 短路链、`_download_segmented` 旧下载路径都还在。留退路是对的，但要有「保留到什么时候」的期限。
3. **需求口径散落在会话里**。用户说的「不要 ai 味」「这个串流很不优美」这类原始口径只存在于聊天记录，台账里是转述。→ 值得在台账每条下加一行「用户原话」。
4. **测试事故的教训要固化**。BUG-020 验证时脚本自动点了确认框，把整张专辑连 B 站收藏一起删了（后来用 `POST /api/imports` 恢复）。→ 危险路径的验证脚本应该默认走 dry-run。
5. **Android 依赖锁定**（BUG-023 的根因）。Chaquopy 环境的 pydantic 版本与开发环境不一致这件事，直到 CI 炸了才发现。→ 环境矩阵写进 CI，别靠记忆。
