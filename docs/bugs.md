## BUG-001 收藏夹同步只拿到子集（多设备数量各不相同）｜ P0 ｜ v1.0.1 已修

**现象**：同一 B 站账号在多台设备登录，App 曲库数量各不相同（用户实测 11 / 18），而 B 站 `bilimusic` 收藏夹实际有 **30** 个视频。

**根因**：`app/bili/client.py` 的 `get_fav_videos()` 用响应里的 `media_count` 当翻页终止条件：

```python
total = int(data.get("media_count") or 0)      # 该接口顶层没有 media_count → 恒为 0
...
if not medias or (total is not None and len(out) >= total): break   # 20 >= 0 → 第一页就 break
```

`/x/v3/fav/resource/list` 把 `media_count` 放在 `data.info` 里，**顶层为 None**，于是 `total=0`，循环永远只翻第一页（ps=20）。收藏夹按收藏时间排序，新收藏会把旧视频挤出前 20 —— 所以每台设备各自停在「当时的前 20 条」，表现为不同子集。

**修复**：终止条件改用响应里的 **`has_more`**；页数上限由 `cap` 计算（不再硬编码 50 页）。`submit_fav`（收藏夹链接批量导入）走同一函数，一并修复。

**验证**（用用户账号真实 cookie 实测）：

| 收藏夹 | 修复前 | 修复后 |
|---|---|---|
| `bilimusic`（30 个） | 20 ❌ | **30** ✅ |
| `默认收藏夹`（28 个） | 20 ❌ | **28** ✅ |

用户真机确认：多设备曲库数量与 B 站收藏夹一致。

## BUG-002 移动端短信登录：极验滑块不渲染 ｜ P1 ｜ v1.0.0 修，v1.0.1 改为下线

**现象**：Android 上填手机号点「获取验证码」，极验验证窗口不出现（或出现但不可见），无法完成短信登录。

**根因**：`MainActivity` 的 WebView 只开了 `setJavaScriptEnabled` + `setDomStorageEnabled`，缺两样极验必需项：
1. 默认 UA 含 `; wv` → 被风控识别为 WebView，不下发滑块；
2. 跨站脚本（`static.geetest.com`）的第三方 Cookie 被拦 → 极验会话拿不到。

**修复**：伪装成手机 Chrome UA（`Mobile Safari/537.36`）、`setAcceptThirdPartyCookies(true)`、`setDatabaseEnabled(true)`、`setMixedContentMode(ALWAYS_ALLOW)`。页面布局走 CSS 视口断点，不受 UA 影响。

**后续**：短信登录体验仍不理想（依赖极验 CDN，跨境线路慢），v1.0.1 整体下线，改为二维码方案（见 FEAT-001）。

## BUG-003 验证参数接口偶发超时，前端只显示笼统失败 ｜ P1 ｜ v1.0.1 已修

**现象**：手机端点「获取验证码」直接提示「验证参数获取失败」，无法排查。

**根因**：`passport.bilibili.com/x/passport-login/captcha` 实测 **3 次里 1 次 ConnectTimeout**（经代理/VPN 更明显）；后端异常未转成可读响应，前端 `r.ok ? r.json() : null` 拿到 null，统一显示笼统文案。

**修复**：`captcha_get()` 网络类错误重试 3 次 + 单次超时 20s→5s（失败也快）；`/api/auth/captcha` 把 `BiliApiError`/`httpx` 错误转成 `502 + detail`；前端直接展示 detail。实测 5/5 成功、耗时 0.8~1.6s。

## BUG-004 曲库计数与 B 站收藏夹口径不一致 ｜ P1 ｜ v1.0.0 已修

**现象**：本地「我的曲库」显示 12，但 B 站收藏夹有 20+，歌单详情页又显示 13，三处对不上。

**根因**：本地计数是「已收藏的**歌曲**数」（`collected=1`），B 站是「收藏的**视频**数」；一个多 P 合集在 B 站算 1 条、在本地算 0~N 首（取决于是否逐曲收藏）。收藏后侧边栏还没刷新，进一步放大了偏差。

**修复**：计数改为**视频级**——收藏单曲 1 条 + 合集容器 1 条；曲库详情页新增「合集」货架，让计数与内容一致；收藏/移出时触发 `playlistsChanged` 刷新侧栏。

## BUG-006 音频流按 id 取最大选档，放开高音质后会选错 ｜ P1 ｜ `[待修]`（用户要求先记不修）

**现象**：目前无感。一旦支持杜比/Hi-Res，会**挑到 192K 而不是 Hi-Res**。

**根因**：`app/bili/quality.py` 的 `pick_best_audio()` 用 `max(streams, key=lambda s: s.quality_id)`，
但 B 站音质 id 的**数字大小 ≠ 音质高低**：

| id | 档位 |
|---|---|
| 30216 | 64K |
| 30232 | 132K |
| 30280 | **192K** |
| 30250 | 杜比全景声 |
| 30251 | **Hi-Res 无损** |

`max(id)` 在所有档位里会选到 **30280（192K）**，把 30251（Hi-Res）/ 30250（杜比）排在后面。

**当前为何不炸**：`client.py` 请求 playurl 用的是 `fnval=16`（仅基础 DASH），B 站只返回
30216/30232/30280 三条 AAC 流，`max(id)` 恰好等于 192K —— 属于「巧合正确」。

**修复方向**（用户要求暂缓）：
1. 改为按 `bandwidth` 降序（同码率再用质量优先级 tie-break）——`AudioStream` 已经存了 `bandwidth`；
2. 若后续放开 `fnval=4048`，另需处理 `dash.flac.audio`（无损）与 `dash.dolby.audio[]`，
   优先 flac → dolby → dash.audio 按带宽取最高；
3. 注意 FLAC/Hi-Res 码率约 1000+ kbps，本服务是**实时代理不落地**，建议 Wi-Fi 优先无损、蜂窝自动降档。

**参考**：`wood3n/biu` 的 `src/common/utils/audio.ts`（`sortAudio` 主键 bandwidth 降序 +
`audioQualitySort` 优先级）与 `electron/ipc/api/audio-stream-url.ts`（带 Cookie/Referer/UA +
按会员状态选 quality）。

## FEAT-001 登录方式改为「点二维码 → 存相册 + 拉起 B 站 App」｜ v1.0.1

**背景**：短信登录依赖极验（见 BUG-002/003），体验差；扫码在单手机上又不方便（没法用同一台机器扫自己的屏幕）。

**方案**：登录弹窗改为**单列扫码**，点二维码后：
1. Android 经原生桥 `saveQrToGallery` 写入系统相册（API 29+ 走 scoped storage 免权限；≤28 申请 `WRITE_EXTERNAL_STORAGE`）；
2. `openBilibiliApp` 拉起 B 站 App；
3. 用户在 B 站 App「扫一扫 → 相册」选中该二维码即可确认登录，后端轮询到确认自动进入；
4. 浏览器/桌面回退为直接下载 PNG。

**前提**：B 站 App 的「扫一扫」需有相册入口（用户侧确认）。

## BUG-007 网易云错配被当成「命中」，不再降级到下一级歌词源｜ P1 ｜ 已修（未打包）

**现象**（用户实测）：部分歌拿到**完全不对**的歌词，来源角标却显示「网易云」，并且**不会继续尝试下一级**
（B 站 AI 字幕 / LRCLIB 纯文本）。用户判断：「网易云会识别到错误的歌词，但是也是识别到了，而不是转到下一级
——我觉得这个兜底机制有问题。」典型触发场景：周杰伦等歌手网易云无版权。

**根因**（`app/services/lyrics.py` → `_from_netease`，L307-322）：

1. **唯一门槛是时长，且时长未知时门槛消失**
   ```python
   if duration and duration_ms and abs(duration_ms / 1000 - duration) > _DURATION_TOLERANCE:
       continue
   ```
   `duration` 为 0（未解析到）时任何搜索结果都直接通过，无任何其他校验。

2. **搜索结果大多是翻唱/同名曲，时长恰好落进 ±3s 就采纳**。用真实接口实测（`Referer: music.163.com`）：
   | 查询 | 网易云返回（时长） |
   |---|---|
   | `周杰伦 晴天` | 全是翻唱：`晴天 (原唱 周杰伦) - RyaVocal` 270s、`晴天(深情版) - Lucky小爱` 278s、`晴天 (女声版))` 268s、`晴天 (钢琴版)` 238s、`晴天 - 梦里啥都有` 228s |
   | `稻香 周杰伦` | `稻香 - Montagem` 183s、`稻香(正式版) - 沈幼楚` 54s、`稻香 - 何兵兵` 121s、`稻香 - Lucky小爱` 231s、`稻香 - Lie` 196s |

   原唱《晴天》269s → `RyaVocal` 270s **命中 ±3s**；原唱《稻香》223s → 这批靠时长被挡掉，
   但 B 站视频若是 CUT/片段（时长接近 183s 或 231s）就会采纳 `Montagem` 那条——它的歌词是
   「稻香，稻香，稻香／那年夏天 我们一起／躺在草地上看星星」，**同名但完全另一首歌**。
   `沈幼楚` 那条 54s 是一段念白（「·通常大家认为 人和人的感情像水一样…」）。

3. **「带轴」判定可被全零时间戳骗过**
   ```python
   if lyric and _SYNCED_HEAD_RE.search(lyric[:200]):   # _SYNCED_HEAD_RE = \[\d{1,2}:\d{2}
   ```
   网易云歌词头部常带 `[00:00.000] 作词 : xxx`，前 200 字必然命中正则；`沈幼楚` 那条 12 行**全是**
   `[00:00.000]·…`，同样判为「带轴」——但所有行时间都是 0，前端 `parsed.timed = timed >= 2` 也成立，
   高亮会全部挤在 0 秒。

4. **首个可接受结果直接 return，不排序也不复核标题/歌手**。对比同文件 `pick_lrclib_result`
   （rank = 带轴优先 + 时长最接近优先），`_from_netease` 的 for 循环里是「第一个通过就返回」，
   且从不比对 `item["name"]` / `artists` 与候选歌名。

5. **链路命中即短路**（`fetch_for_song` L165-167）：错误的 ncm 结果会**挡住**后面的 B 站 AI 字幕
   （对翻唱视频而言 AI 字幕往往是**对的**）与 LRCLIB 纯文本。

**附带现象**：LRC 元数据行未被过滤。前端 `NOTE_RE` 只剥 `♪♫♩♬`（`app.js:754`），
所以 `晴天 (原唱 周杰伦)` 的歌词会把 `作词 : Chieh-lun Chou`、`作曲 : Chieh-lun Chou`、
`编曲 : 周杰伦` 当成歌词行显示在最前面。

**修复方向**（用户要求先攒台账，未开工）：

- **A. 置信度判定，不达标就降级而不是 return**
  - 时长未知 → 外部源一律要求歌名**完全相等**才采纳；
  - 采纳前复核返回歌名/歌手与候选的相似度（归一化后相等或包含）；
  - 拒绝退化时间轴（不同非零时间戳 < 3 个，或末行时间 < 时长 50% 且行数 > 6）；
  - 行数下限（≥8）+ 时间覆盖率下限。
- **B. 改「多源候选 + 打分选最优」**：各源产出（文本, 源, 分数），统一排序；最高分低于阈值即视为未找到，
  继续降级。这是用户诉求「错的不该挡住下一级」的结构性解法。
- **C. 无版权歌手的正确兜底**：网易云无版权时应该**拿不到**（现状是拿到错的）——
  真正该承担的是 LRCLIB（《晴天》《稻香》都有带轴）+ B 站 CC/AI 字幕 + 视频简介；
  再加手动搜索 + 歌词偏移（`wood3n/biu` 已有）。
- **D. `_SYNCED_HEAD_RE` 换成 `_looks_synced(lyric, duration)`** 做真实时间轴校验。
- **E. 元数据行清洗**：剥掉 `作词/作曲/编曲/OP/SP/制作人 :` 等头部行，前端与后端各一道。

**现有兜底**：歌词页来源角标（`#lyrics-source`）+ `↻` 重试按钮（`/api/songs/{id}/lyrics?force=1`）——
但重试会**再走同一条链路**，命中同一个错配结果，对用户没有帮助。

**实测铁证**（用户库中唯一一条 `ncm` 结果，song id 415）：

| 项 | 值 |
|---|---|
| B 站视频 | `【Rammstein】德国战车 MV精选（DVD） · Ich tu dir weh`（UP：david_-young，237s） |
| 网易云给的歌词 | `[00:00.00] 作词 : Jaymes Young/Billboard …` / `Baby this love` / `I'll never let it die` |
| 实际是 | **Jaymes Young《Infinity》**——另一首歌的歌词 |

另一条 `ai` 结果（song id 127，现场演出）内容是「出去吧／这是一只／♪ 音乐 ♪／宝宝／
有人想这么做吗」——AI 字幕当歌词同样不合格。即：**当前库里两条非 CC 结果全是坏的**。

### 修复（`app/services/lyrics.py`，未打包）

1. **置信度校验 `match_confidence()` / `accept_external()`**——外部源（LRCLIB / 网易云）命中项必须：
   - 双方时长已知且相差 ≤3s（**硬门槛**）；
   - 歌名归一化后相等或互相包含（**硬门槛**）；
   - 综合打分达阈值：歌名相等 +3 / 包含 +2、歌手出现在标题或 UP 主里 +3、
     时长 ≤1.5s +3 / ≤3s +2、带真实时间轴 +1（满分 10）；
   - 严格阈值 **7**（`BM_LYRICS_STRICT=1`，默认），放宽阈值 4（`BM_LYRICS_STRICT=0`）。

   不合格就当这一源没结果，**继续降级**——这是用户诉求「错的不该挡住下一级」的落点。
2. **时间轴真实校验 `looks_synced()`**：≥4 个带轴行、≥3 个不同非零时间、末行不早于时长 40%；
   替掉只看前 200 字有没有 `[mm:ss` 的旧判定（会被 `[00:00.000] 作词 : xxx` 与全零时间戳骗过）。
3. **元数据行清洗 `strip_meta_lines()`**：落库前剥掉 `作词/作曲/编曲/制作人/OP/SP…` 行；
   前端 `parseLrc` 也加一道（老库里已存的也能干净显示）。
4. **网易云默认关闭**（`BM_LYRICS_NETEASE=1` 才启用）；启用时改为**取得分最高**的一条，
   不再「第一个通过就返回」。
5. **候选不再截断**：去掉 `_from_netease` 的 `[:2]`，与 `_from_lrclib` 共用候选列表。

强制刷新后全库来源分布：`cc 32 / lrclib 2 / ai 1 / 空 2`，**ncm 归零**，库内已无元数据行残留。

## BUG-008 合集/分P 标题的歌词候选提取把真歌名丢掉｜ P1 ｜ 已修（未打包）

**现象**：多P合集里的曲目（标题形如「合集标题 · 分P标题」）几乎永远拿不到外部歌词，
即使 LRCLIB 明明有——《兰亭序》《菊花台》《Sonne》都有带轴版本。

**根因**：`app/services/lyrics.py` → `title_candidates()` 先按 `[|｜/·◆★\-—–\s]+` 切段，
合集标题被切成一堆噪声段（「50首精选合集」「后台播放」「无损音质」…），
真正的歌名排在最后，而函数末尾 `return out[:4]` 恰好把它截掉。实测：

```
title_candidates("【周杰伦】50首精选合集/后台播放/无损音质/HIFI音质/华语流行音乐才是最叼的 · 周杰伦-兰亭序")
-> ['50首精选合集 后台播放 无损音质 HIFI音质 华语流行音乐才是最叼的 周杰伦 兰亭序',
    '50首精选合集', '后台播放', '无损音质']          # ← "兰亭序" 被 [:4] 截掉
```

`_from_netease` 更是只取 `title_candidates(title)[:2]`，连第三段都够不到。

**实测影响**（用户曲库抽样 121 首，其中 33 首无 CC 字幕）：

| 候选策略 | LRCLIB 命中 |
|---|---|
| 现状（`title_candidates`） | **0 / 33** |
| 优先取「 · 」后的分P标题 | **20 / 33（全部带轴）** |

命中的 20 条里 18 条明显正确（周杰伦 10 首时长几乎完全吻合：兰亭序 254/254、
听妈妈的话 266/266、菊花台 294/294、彩虹 264/264；Rammstein 8 首），
2 条同名撞车（`Sonne (3)` → `Schwarze Sonne / RAF 3.0`；巡演视频 → `No Strings Attached / 'N Sync`）。

**修复方向**：

1. `title_candidates()` 识别「 · 」结构：**分P标题优先**成候选，主标题段降到后面；
2. 候选上限 4 太小 → 提高，或按「像歌名的程度」排序；
3. `_from_netease` 的 `[:2]` 与 `_from_lrclib` 的 `[:4]` 统一走同一套候选排序；
4. 配合 BUG-007 的歌手/歌名复核，处理上面 2 条同名撞车。

**与 BUG-007 的关系**：两者叠加才是「网易云错配」的完整图景——候选错误让搜索引擎搜到
不相干的歌，接受门槛过松又让它被直接采纳。

## BUG-009 多P合集子曲目标题重复拼接合集名（专辑页每行一长串）｜ P2 ｜ 已修（未打包）

**现象**（用户截图）：专辑页每行曲目名都是
`【周杰伦】50首精选合集/后台播放/无损音质/HIFI音质/华语流行音乐才是最叼的 · 001.周杰伦-晴天`，

**根因**：`app/services/importer.py` 的 `part_display_title()` 有意把主标题拼在前面
（`return f"{main} · {cleaned}"`），子曲目标题按此入库，所有展示位直接用 `song.title`。

**修复**：

1. 新增 `app/services/titles.py`：`clean_part_title()` / `is_meaningful_part()` /
   `part_display_title()` / `short_title()`——子曲目标题**只保留分P名（歌名）**，
   占位名（`P1` / `正片` / 空）才回退主标题；单字中文歌名（`枫`）算有效歌名，
   不按长度一刀切。
2. `importer.py` 改用新 helper（单视频带分P、多P专辑子曲目两处构造点）。
3. `db/session.py` 新增**幂等**迁移 `_shorten_album_child_titles()`：把存量
   「合集标题 · 分P标题」收敛为分P标题。只在确实知道 `album.title` 时收敛，
   **不误伤**标题本身带 ` · ` 的曲目（例如 UP 主原标题
   `黄小琥《没那么简单》 但是方大同风格编曲 · 没那么简单` 保持原样）。

**验证**：用户库 518 条待收敛 → **0 条**；专辑 2 的曲目从

## FEAT-002 手机端底部悬浮组：导航条 + 播放条尺寸统一 + 液态玻璃选中块｜ 已改（未打包）

**诉求演进**（用户逐轮反馈）：选中块不要粉色渐变 → 要跟手拖动 + 水珠形变 → 圆角/间距要与导航条

形变要变成竖椭圆并可**溢出**条子 → 上方播放条也要改成与导航条同等大小。

**最终规格**（`app/web/static/style.css` 手机媒体查询 + `app/web/static/nav-liquid.js`）：

| 项 | 值 |
|---|---|
| 悬浮组公共变量 | `--nav-pad:6px` · `--nav-tabw:78px` · `--nav-gap:10px` · `--nav-orb:64px` · `--nav-h:66px` |
| 导航条 | 内容宽度（248px）居中，高 66px，圆角 999px |
| 播放条 | 宽 = 导航条 + 间距 + 圆钮 = **322px**，高 **66px**，与导航条左边缘对齐（x=89） |
| 圆钮 | 64px |
| 选中块（静止） | 78 × 52，四周留白 6px，与导航条内缘**同心**（圆心 x=67 完全重合） |
| 选中块（拖动最大） | 0.44 / 1.42 → **34 × 74px**，上下各**溢出条子约 4px**（水珠挤出效果） |
| 长按 | 0.69 / 1.23 |
| 弹簧 | 拖动中 k=0.24 / d=0.42（滞后量=水珠形变来源）；松手/切换 k=0.14 / d=0.84（过阻尼，零过冲，整格 512ms） |
| 吸附 | 当前格 +0.15 格惩罚（走 35% 就切）；松手速度 vel×0.25 限幅 ±5 |
| 窄屏（≤370px） | `--nav-tabw:66px` · `--nav-orb:58px` · `--nav-h:62px` |
