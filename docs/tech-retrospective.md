## 0. 坑的分类学

这个项目的坑不是随机分布的，集中在六个地方。按「修起来最贵」排序：

| 类别 | 典型 | 为什么贵 |
|---|---|---|
| **外部接口的隐含语义** | 分页字段位置（BUG-001）、音质 id 大小≠质量（BUG-006）、收藏粒度（BUG-020） | 接口不报错，只是「安静地给你错的答案」，测不出来 |
| **异步与竞态** | 跨端接管被旧快照打回（#27）、内嵌后端启动竞态、账号激活失败降级 | 只在特定时序出现，本地复现难 |
| **渲染与层叠** | `.main` 层叠上下文陷阱（BUG-012）、`backdrop-filter` 闪一下就失效、重复 CSS 规则互相覆盖（BUG-013） | 代码「看起来是对的」，浏览器就是不听 |
| **依赖与环境漂移** | Chaquopy 的 pydantic 1.10（BUG-023）、Cargo 三段式版本号、Windows 编译 macOS API | 本地全绿，CI/真机炸 |
| **前端平台差异** | 键盘遮挡（BUG-010 #5）、WebView 不渲染 backdrop-filter、安全区 | 需要真机或精确仿真才能发现 |
| **数据迁移的历史包袱** | 标题前缀回填（BUG-009）、`collected` 标记迁移 | 改错会伤到用户已有数据，只能幂等 + 保守 |

## 1. B 站接口：安静的错误最贵

### 1.1 分页终止条件用错了字段（BUG-001，P0）

**现象**：同一账号在三台设备上，曲库数量各不相同（11 / 18），而 B 站收藏夹实际有 30 条。

**根因**：`/x/v3/fav/resource/list` 返回的 `media_count` 在 **`data.info` 里**，顶层没有这个字段，于是：

```python
total = int(data.get("media_count") or 0)   # 顶层为 None → total 恒为 0
...
if not medias or (total is not None and len(out) >= total): break   # 20 >= 0 → 第一页就 break
```

收藏夹按收藏时间排序，新收藏会把旧的挤出前 20 —— 每台设备各自停在「当时的前 20 条」，所以数量不同。

**修法**：终止条件改用响应里的 **`has_more`**；页数上限由 `cap` 计算，不再硬编码 50 页。`submit_fav`（收藏夹链接批量导入）走同一函数，一并修复。

**验证**：用真实 cookie 实测 —— `bilimusic`（30 条）修前 20 / 修后 30；`默认收藏夹`（28 条）修前 20 / 修后 28。

**防再犯**：分页 API 的终止条件**永远优先用响应自带的 `has_more` / `next` 游标**，不要用「我猜的总数」。如果非要用计数，先打日志确认它到底在响应的哪一层。

### 1.2 音质档位的 id 大小 ≠ 音质高低（BUG-006，未修）

**现象**：目前无感，一旦支持杜比/Hi-Res 会挑错档。

**根因**：`pick_best_audio()` 用 `max(streams, key=lambda s: s.quality_id)`，但 B 站音质 id 是**编号不是等级**：

| id | 档位 |
|---|---|
| 30216 | 64K |
| 30232 | 132K |
| 30280 | 192K |
| 30250 | 杜比全景声 |
| 30251 | **Hi-Res 无损** |

`max(id)` 会选到 30280（192K），把 30251 / 30250 排在后面。

**当前为什么不炸**：请求用的是 `fnval=16`（仅基础 DASH），B 站只返回 30216/30232/30280 三条，`max(id)` 恰好等于 192K——**属于「巧合正确」**。

**正确修法**（已写入台账，等排期）：改为按 `bandwidth` 降序（同码率再用质量优先级 tie-break）；如果放开 `fnval=4048`，还要处理 `dash.flac.audio` 与 `dash.dolby.audio[]`。

**防再犯**：任何「取最优」的代码，如果排序键是**枚举值**而不是**可比较的度量**，就要停下来问一句：这个枚举的大小有意义吗？

### 1.3 收藏粒度是 `(bvid, cid)` 不是 `bvid`（BUG-020）

**现象**：只听过《爱我别走》从没收藏，播放条星星却是粉的；而专辑列表里那行是灰的。

**根因**：前端收藏表只按 `bvid` 记，而《爱的初体验》(cid 1405147297) 与《爱我别走》(cid 1405147389) 是**同一个视频的两个分 P**——bvid 相同，于是命中了已收藏表。

**修法**：

- 后端 `song_out` 补 `cid`；
- 前端收藏表键改为 `bvid:cid`（`songKey()` / `currentRef()` / `currentKey()`）；
- 星星点击：当前歌在曲库里有行时走 `POST /api/songs/{id}/collect`（**精确认领这一首**），无行（试听流）才回退整视频导入。

**防再犯**：凡是「收藏 / 下载 / 播放进度 / 去重」这类幂等键，先明确**业务粒度**是什么。多 P 视频是这个项目里最容易出错的结构——B 站算 1 条，本地算 N 首。

### 1.4 链接形态与 sid 前缀

系列合集的 `source_bvid` 存的是 `"sid:777"` 这种**伪 bvid**。前端按 bvid 拼链接，就拼出了 `https://www.bilibili.com/video/sid%3A777`——一个打不开的地址。

**修法**：新增 `app/core/share_links.py`，纯函数拼链接（`video_link` / `fav_folder_link` / `series_link` / `series_sid` / `album_share_url`），**缺字段返回空串，绝不拼半截链接**；系列缺 mid 时用任一曲目 bvid 反查 UP 回填，反查失败就明确报「拿不到合集来源 UP」（409 可读文案），而不是产生废链。

## 2. 账号、登录与风控

### 2.1 账号隔离：切换账号后看到上一个账号的数据（09-06 ~ 09-07）

**现象**（用户原话）：「扫码后仍未登录、切换账号后看到上一账号的数据」「我登陆另一个账号，显示没有登陆态」「短信，扫码都试了，都失败」。

**修法方向**（`c2b4e30` 大提交 + `app/services/accounts.py` 新增）：

- 引入 `account_scope(mid)` 上下文 + 按 mid 分目录的数据库/凭据（`account_db_path(mid)` / `account_cookie_path(mid)`）；
- 中间件按 mid 隔离（`account_scope` 中间件）；
- 活跃账号标记 `active_mid` 文件 + `activate_account()` / `reset_to_pending()`；
- 前端账号切换后清空本地会话状态。

**防再犯**：多账号系统里，「当前账号」必须是一个**显式的、可被中间件读到的**作用域，而不是散落在各处的全局变量。

### 2.2 WebView 里极验滑块不渲染（BUG-002）

**根因**两条，缺一不可：

1. WebView 默认 UA 含 `; wv` → 被风控识别为 WebView，不下发滑块；
2. 跨站脚本（`static.geetest.com`）的第三方 Cookie 被拦 → 极验会话拿不到。

**修法**：伪装成手机 Chrome UA（`Mobile Safari/537.36`）、`setAcceptThirdPartyCookies(true)`、`setDatabaseEnabled(true)`、`setMixedContentMode(ALWAYS_ALLOW)`。页面布局走 CSS 视口断点，不受 UA 影响。

**结局**：即使修好，短信登录体验仍不理想（依赖极验 CDN，跨境线路慢）→ v1.0.1 整体下线，改二维码方案。

**经验**：**外部验证码服务的 WebView 兼容性是个无底洞**。能绕就绕。

### 2.3 验证码接口偶发超时，前端只显示笼统失败（BUG-003）

**根因**：`passport.bilibili.com/x/passport-login/captcha` 实测 **3 次里 1 次 ConnectTimeout**（经代理/VPN 更明显）；后端异常没转成可读响应，前端 `r.ok ? r.json() : null` 拿到 null，统一显示笼统文案。

**修法**：网络类错误重试 3 次 + 单次超时 20s → 5s（失败也要快）；`/api/auth/captcha` 把 `BiliApiError` / `httpx` 错误转成 `502 + detail`，前端直接展示 detail。实测 5/5 成功、耗时 0.8 ~ 1.6s。

**经验**：**错误信息是产品的一部分**。「验证参数获取失败」和「网络超时，已重试 3 次」对用户和排障者是两个世界。

### 2.4 启动时网络抖动 → 账号被降级为「未登录」（BUG-022）

**根因**：`app/main.py` lifespan 里 `accounts.activate()` 是**一次性的**——任何异常都直接 `dbs.reset_to_pending()`。网络类错误（`httpx.RemoteProtocolError`）与「凭据失效」被同等对待。结果：`cookies.json` 里的 SESSDATA 完好，但所有 `/api/*` 返回 401，**必须重启一次才恢复**。

**修法**：网络类错误（`httpx.HTTPError` / `OSError` / `ConnectionError`）重试 2 次（1.5s、3s 退避）；凭据失效（`BiliApiError`）不重试、按需重新登录；**全部失败才 reset 到 pending**。

**验证**：重启后端 6 次（含一次真实抖动）稳定恢复。

**经验**：**区分「暂时连不上」和「确实没权限」**。这是所有带登录态的服务端都要做的一次分类。

## 3. 歌词：多源兜底的正确姿势

### 3.1 网易云错配被当成「命中」（BUG-007）

**现象**（用户原话）：「网易云会识别到错误的歌词，但是也是识别到了，而不是转到下一级——我觉得这个兜底机制有问题。」

**根因链**（全部有真实接口实测证据）：

1. **唯一门槛是时长，且时长未知时门槛消失**：`if duration and duration_ms and abs(...) > tol: continue`——`duration=0` 时任何结果都通过；
2. 搜索结果大多是翻唱/同名曲，时长恰好落进 ±3s 就采纳。实测：查「周杰伦 晴天」返回的全是翻唱（`晴天 (原唱 周杰伦) - RyaVocal` 270s 等），原唱 269s → **命中**；
3. **「带轴」判定被全零时间戳骗过**：网易云歌词头部常带 `[00:00.000] 作词 : xxx`，前 200 字必然命中正则；有条结果 12 行**全是** `[00:00.000]·…`，照样判为带轴；
4. **首个可接受结果直接 return**，不排序也不复核标题/歌手；
5. **链路命中即短路**：错误的 ncm 结果会挡住后面的 B 站 AI 字幕与 LRCLIB —— 而对翻唱视频而言 AI 字幕往往是**对的**。

**修法**：置信度判定（时长未知 → 外部源要求歌名完全相等；采纳前复核歌名/歌手相似度；拒绝退化时间轴）+ 不达标降级而不是 return + 网易云默认关闭。修后全库来源分布 `cc 32 / lrclib 2 / ai 1 / 空 2`，**ncm 归零**。

**残留（诚实记录）**：id 391「Sonne (3)」拿到俄语翻唱版（同名 + 时长巧合，歌手对不上但没触发硬门槛）。要彻底挡住得把歌手校验改成必过，代价是丢掉一批标题里没歌手名的正确命中——暂不采用。

### 3.2 候选提取把真歌名丢掉了（BUG-008）

**现象**：多 P 合集里的曲目几乎永远拿不到外部歌词，即使 LRCLIB 明明有。

**根因**：`title_candidates()` 按 `[|｜/·◆★\-—–\s]+` 切段，合集标题被切成一堆噪声段，真歌名排在最后，而函数末尾 `return out[:4]` 恰好把它截掉：

```
title_candidates("【周杰伦】50首精选合集/后台播放/无损音质/HIFI音质/华语流行音乐才是最叼的 · 周杰伦-兰亭序")
-> ['50首精选合集 后台播放 无损音质 HIFI音质 华语流行音乐才是最叼的 周杰伦 兰亭序',
    '50首精选合集', '后台播放', '无损音质']          # ← "兰亭序" 被 [:4] 截掉
```

`_from_netease` 更狠，只取 `title_candidates(title)[:2]`。

**修法**：识别「 · 」结构，**分 P 标题优先成候选**，整串标题排在后面；上限从 4 提到 6；清洗逻辑抽成 `_candidates_from()` 复用。

**效果**（用户曲库抽样 121 首，其中 33 首无 CC 字幕）：现状 `title_candidates` 命中 LRCLIB **0 / 33**；改成「优先取 ` · ` 后的分 P 标题」后 **20 / 33**（全部带轴，其中 18 条明显正确，2 条同名撞车）。

### 3.3 覆盖率实测（这是最有价值的一张表）

用真实 cookie 抽样 120 首统计：

| 来源策略 | 覆盖 | 备注 |
|---|---|---|
| 仅 B 站人工 CC 字幕 | **87 / 120 = 72.5%** | 已收藏曲目 **20/20 = 100%**；未收藏（多 P 子曲目）67/100 |
| CC + AI 字幕 | 90 / 120 = 75% | 只多 2.5pp，且 AI 字幕质量差 |
| CC + LRCLIB（修 BUG-008 后） | **107 / 120 = 89.2%** | 20 条命中里 2 条同名撞车，需歌手复核 |
| 现状全链路（含网易云） | —— | 库里唯一一条 ncm 结果就是错的 |

**结论**：B 站字幕**天然与视频绑定、不可能错配**，但覆盖只有 72.5%；LRCLIB 能把覆盖补到 89%，代价是**必须**加置信度校验。这条结论直接决定了产品的歌词策略：**B 站字幕优先，外部源只做补充且要过校验。**

## 4. 播放与流：卡顿是怎么修好的

### 4.1 先核对别人的方案，再动手（BUG-021）

用户给了一份外部优化方案 docx，逐条核对后的结论：

| 方案里的说法 | 核对结果 |
|---|---|
| ① 首次播放要等整文件下载完（应改流式代理） | ❌ 不成立：`/api/stream/{bvid}` 本来就是流式代理（64KB 分块、支持 Range/206、不落盘） |
| ② CDN 多源 Fallback 缺失 | ✅ 成立，已修 |
| ③ httpx 连接未复用 | ❌ 不成立：`BiliClient.http` 是实例级单例 `AsyncClient` |
| ④ 前端无预缓冲 | ✅ 部分成立：主 `<audio>` 是 `preload="none"`，且没有 `waiting/stalled` 恢复 |
| ⑤ 重试太简单 | ⚠️ 位置过时：那段属旧下载路径；流式路径**完全没有**重试 |

**真正的根因**：Android 侧 `MediaPlaybackService` 只有前台服务 + MediaSession，**没有 WakeLock / WifiLock**——息屏后 CPU 与 Wi-Fi 一起打盹，流式音频断供。这就是「锁屏/后台/切前台才卡」的典型成因。

**修法三件套**：

1. **Android**：播放期间持 `PARTIAL_WAKE_LOCK` + `WIFI_MODE_FULL_HIGH_PERF`，暂停/停止/销毁即释放；Manifest 加 `WAKE_LOCK` 权限；
2. **后端**：`/api/stream` 按 `candidate_urls()`（base + backup CDN）换源重试，连接层失败或 4xx/5xx 都换下一个镜像，每次 0.3s 递增退避，全部失败才 502（文案说明「已尝试全部镜像」）；**只在首字节之前换源**，开始推流后不切；
3. **前端**：`preload="auto"` + 卡顿自愈（`waiting/stalled/error` 后 3 秒仍未恢复且未暂停 → 在当前进度重开一次；15 秒冷却、连续 5 次上限；正常 `playing` 即清零）。

**明确不采纳**：换 howler.js / hls.js（会丢掉双轨交叉淡入与歌词联动，且 B 站给的是 m4s 直链不是 HLS）；给 `/api/stream` 加 `Cache-Control: max-age=86400`（对 Range 代理有害）。

**经验**：**性能问题先证伪再动手**。这份方案里 5 条有 2 条是错的、1 条位置过时——照着改会白干，还会引入新问题。

### 4.2 流式代理的几个设计点

- 支持 Range/206 —— 拖进度条才能用；
- 不落盘 —— 顺带绕开了磁盘占用与盗链时效；
- 换源只在首字节前 —— 一旦开始推流再切换会造成播放器解码中断；
- 刻意不给 `/api/stream` 加 `no-store` —— 让浏览器缓存能正常工作。

## 5. 跨端会话：这个项目最难的并发问题

### 5.1 设计前提

**跨端接力转移的是「会话状态」，不是音频数据**——接收端自己向后端取流并 seek 到目标位置。三条有利条件：

| 条件 | 证据 |
|---|---|
| 音频由后端代理，任何设备可独立解析同一条流 | `/api/stream/{bvid}?cid=` |
| SSE 事件总线按 mid 过滤，天然支持多订阅者 | `app/events.py` `_subs: set[tuple[mid, Queue]]` |
| 进程内任务单例有成熟先例 | `SyncState` / `ExportState` |

### 5.2 竞态一：接管后被在途旧快照打回暂停（#27）

**现象**：「点了串流到本设备，本机却没声音」（端到端 ④ 连挂 3 次）。

**根因**：SSE 事件与上报响应是**两条独立通道**，接管成功那一瞬间会送到**接管之前生成**的快照（`active` 仍指着上一台设备）；`applySnapshot()` 照单全收 → `handOverLocally()` 误判「我被抢走了」→ 淡出暂停。调用栈实证：`pause()` 来自 `session-sync.js:199` 的 `handOverLocally`，而服务端 `active` 一直是本机。

**修法**：接管成功时记下会话 `revision`，之后凡比它更旧的快照一律作废（快照不带版本号时用 8s 接管宽限窗兜底）—— `claimRev` / `claimFrom` / `applySnapshot()`。

**并留下一条回归探针**：e2e 的 ④b 会**人为注入一条「上一台仍 active」的在途旧快照**，断言本机必须继续出声、不退回镜像。这是把「踩过的坑」变成「永久护栏」的标准做法。

### 5.3 竞态二：发送端在淡出期间把会话抢回去（#23 Phase 3）

**现象**：接管成功后 active 又变回发送端。

**根因**：发送端在 350ms 淡出期间仍上报 `playing=true`。

**修法**：① 客户端一开始让出就按「已暂停」口径上报；② 服务端加 `TAKEOVER_GRACE = 2.5s` 宽限窗——刚被接管/被抢占的会话在此期间不接受旧设备的 `playing` 抢回（单测覆盖）。

### 5.4 移交握手的容错设计

- 移交 12s 兜底超时（`TRANSFER_TIMEOUT`），快照里带 `transfer` 状态；
- 非 active 设备发命令按 `target-offline` / `self-active` / `stale-revision` 分类拒绝（409）；
- 接收端流程：等现报（≤800ms）→ `BiliPlayer.prepare()`（预加载 + seek，5s `canplay` 超时）→ `resume()` → `POST /api/session/claimed`；
- 失败/自动播放被拦 → 渲染「点一下继续播放」（点击即用户手势，重试 claim）；
- 发送端**收到 claimed 才** 300ms 淡出并暂停（不能提前停，否则失败时音乐断了）。

**实测数字**：预加载发起延迟 **5ms**（Phase 2 时要先等现报最多 800ms）；接收端音量 `0 → 0.22 → 0.33 → 0.56 → 0.78 → 0.89 → 1`（约 350ms）；发送端 `1 → 0.78 → 0.67 → 0.44 → 0.22 → 0.11`（同一窗口）。

### 5.5 局域网发现：为什么选「固定端口扫描」

`SessionBus` 是**进程内单例**，两台设备要互相看见必须打到同一个后端进程。而 Android 侧固定加载本机 Chaquopy 内嵌后端（`127.0.0.1` 随机端口）——这是 #26 的根因，**不是 bug 而是设计前提没落地**。

| 方案 | 做法 | 结论 |
|---|---|---|
| A 手工填地址 | 设置项存 `serverUrl` | 最简单，但要手输 IP |
| B mDNS | 桌面注册 `_bilimusic._tcp` + Android `NsdManager` | 体验最好，但要动桌面打包依赖，2~3 天 |
| **B' 固定端口扫描（选它）** | 约定 8000；后端绑 `0.0.0.0:8000`，Android 并发扫 /24 网段逐 IP 试 ping | 零新依赖、全自动无感；只覆盖 /24（家庭网络足够） |
| C 扫码配对 | Mac 出二维码，手机扫码接入 | 还要动原生扫码入口，链路最长 |
| D 不做 | 文档写明前提 | 主场景继续缺位 |

**实现细节**：`lan_socket()` 绑 `0.0.0.0:$BM_PORT`（默认 8000），**端口被占回退 loopback 随机**（本机照常用，只是局域网不可发现）；`GET /api/discovery/ping` 返回 `{app:"bilimusic", name, loggedIn}`，**不设登录门禁**（探测发生在选定后端之前），但保留 token 门禁（配了 `BM_API_TOKEN` 的后端不被陌生设备发现）；Android 侧 /24 网段 64 并发、TCP 250ms。

**账号识别不用明文 mid**：`sha256("bilimusic-lan:" + mid)[:12]`，两端同口径，只做匹配不传输明文。

**安全注记（诚实记录，Mimosa 扫描也提示过）**：桌面后端因此对外监听 `0.0.0.0:8000`。与「默认面向个人局域网部署」的既有立场一致，公网/办公网用户应设 `BM_API_TOKEN`。

### 5.6 手柄势的工程细节（#29）

- `LONG_PRESS_MS = 320`（e2e 断言 180ms 不弹 / 320ms 弹）；
- 浮层锚定在**发起的那颗键**上（手机＝中键、桌面＝设备图标）：横向对中、纵向贴它的上沿，`transform-origin` 也落在那一侧；窄屏贴边；
- 上拖时 `bar.dragging` → 尺寸缩到 58×58 跟手，`#dev-pick.blur` 打开，`scrollY` 始终为 0（浮层与中键都 `touch-action:none`）；
- **e2e 期间抓到的真 bug**：拖拽期间收到快照会重绘设备行，把跟手高亮整条刷掉（落点仍对，视觉丢了）。→ 改成按**设备 id** 记高亮，`renderPick()` 重绘后 `restoreHi()` 补回来；
- 另一个：`.dp-row.hi` 的 `scale(1.02)` 会撑出横向滚动条 → `.dp-body` 补 `overflow-x:hidden`。

## 6. 前端渲染与 CSS：浏览器不会骗你，但会误解你

### 6.1 `backdrop-filter` 的「闪一下就失效」

这是 09-05 那天最耗时的坑，前后改了 12 个提交。过程：加模糊 → 提不透明度 → 学 Apple 配方 → 高不透明雾面 → 关掉 → 全透明 → 纯 `filter: blur(30px)` 镜像层 → Uiverse 配方 → 消除渐变不均匀。

**两条结论**：

1. **`translateZ(0)` / `will-change` 之类的「合成层 hack」正是毛玻璃闪一下就失效的元凶**——移除它（`5ea617a`）；这条与直觉相反，值得记住。
2. 用户 WebView 环境的务实终案：**改用镜像模糊层**（对侧栏背后的内容做模糊，而不是依赖 `backdrop-filter`），全浏览器兼容。

### 6.2 层叠上下文陷阱（BUG-012）

**现象**：UP 作品页里能搜出结果，但**搜索框本身看不见**。

**根因**：`.app .main { position:absolute; inset:0; z-index:0 }`——`.main` 带 z-index 就**自成层叠上下文**。搜索胶囊 `#topbar` 是 `.main` 的子节点，它的 `z-index:130` 只在 `.main` 内部生效；对外比较的是 `.main(0)` vs `#up-panel(90)`，所以胶囊永远被作品页盖住。而结果面板是 `.app` 的直接子节点，抬高 z-index 就有效——这正是「结果看得见、输入框看不见」的原因。

**修法**：`window.__searchBarPortal(on)`——进入手机搜索态时把胶囊临时挂到 `#app` 下（它已是 `position:fixed`，视觉位置不变；`appendChild` 搬家不丢事件监听），关闭时放回 `.main` 首位。桌面端完全不走这条路径。

**验证方法**：`document.elementFromPoint` 命中测试——浏览器判断「谁在最上层」的权威手段。

| 场景 | 胶囊中心命中 | 结论 |
|---|---|---|
| UP 作品页 + 搜索态（修复后） | `input#search` | ✅ |
| 把胶囊放回 `.main` 复现旧行为 | `div#m-dock` | ❌ 被盖住 |

**经验**：调 z-index 之前，先问「这两层在同一个层叠上下文里吗」。只要祖先链上有人带 `z-index` / `transform` / `filter` / `opacity < 1`，比较就发生在那个祖先层。

### 6.3 重复的 CSS 规则互相覆盖（BUG-013）

手机媒体查询里 `.search-drop` **被定义了两次**，后一条把前面带 `var(--kb)` 的 `max-height` 一起盖掉了——BUG-010 #5 的键盘避让其实一直被它削弱，只是没人发现。

**修法**：删掉重复规则，让带 `--kb` 的那份成为唯一来源；同时把搜索胶囊与播放条改成**同一条宽度公式** + `margin-inline:auto`（原来一个是 `left:12/right:12 + width:calc(...)`，另一个是 `left:12; right:86`）。

**量测结果**：390px 视口下两者都 25→365（340 宽）；360px 下都 40→320（280 宽）。

**经验**：**同一个组件只留一处几何定义**，并且写在变量里（`--nav-tabw` / `--nav-pad` / `--nav-gap`）。这个项目后来之所以能修好「播放条与导航栏不等长」（#29 ①），就是因为把 `.m-tabs` 里写死的 `--nav-pad/--nav-tabw` 删掉、统一读 `body` 上的变量。

### 6.4 手机键盘遮挡（BUG-010 #5）

**根因**：旧逻辑只在 `visualViewport.resize` 时给**已存在**的面板写行内 `bottom`；结果面板要等接口返回才出现，早错过了那次事件。

**修法**：把键盘占位高度写成 CSS 变量 `--kb`，胶囊与结果面板的 `bottom` / `max-height` 都带 `var(--kb)`；`resize` / `scroll` / `orientationchange` 都刷新。

**经验**：**事件驱动 → 状态驱动**。不要「在事件里改元素」，要「把事件的结果写进一个状态变量，让元素读它」。

### 6.5 播放条 / 导航条 / 圆钮的「三件套公式」

`FEAT-002` 把底部悬浮组做成一套公共变量：

```
--nav-pad:6px  ·  --nav-tabw:78px  ·  --nav-gap:10px  ·  --nav-orb:64px  ·  --nav-h:66px
导航条 = 内容宽度（248px）居中，高 66px，圆角 999px
播放条 = 导航条 + 间距 + 圆钮 = 322px，高 66px，左边缘对齐
窄屏（≤370px）：--nav-tabw:66px · --nav-orb:58px · --nav-h:62px
```

**踩坑**：`.m-tab{flex:1 1 78px}` 时 Chrome 把容器 intrinsic 宽度算成内容宽度（84px）→ 必须写 `flex:0 0 var(--nav-tabw)`；`.m-tabs` 还要加 padding 让 tab 盒与选中块完全重合，否则最左/最右格圆角与容器内缘不同心。

### 6.6 其他零星

- **安全区**：账号页顶部要叠 `env(safe-area-inset-bottom)`；「加载更多」的下留白从写死 150px 改成 `calc(200px + 安全区)`（BUG-011 差的那 12px 就是这么来的）。
- **磨砂与走马灯**：#12/#13 的左右羽化（`mask-image: linear-gradient(...)`）**挂在标题元素上**而不是走马灯状态上，导致短标题也被吃掉首尾（#28，未修）。
- **iOS 连续曲率**：`corner-shape: superellipse(2)`，合并分支时曾残留错误的 `superellipse(5)`（`2ea61ca` 清理）。

### 7.1 Electron → Tauri 的决策与代价

用户问「如果让你改写为 tauri，减少内存消耗，是否可行？先评估项目，告诉我是否需要重写？」→ 评估后重写（`9d435c2`）。

**代价**：改了 Web 资源后必须 `python packaging/build-backend.py` 重打 bundle 再启动（PyInstaller 内嵌静态资源）——这条后来写进了 `docs/next-steps.md` 的「环境速查」。

### 7.2 Cargo 只接受三段式版本号（`68a679a`）

CI 三个 desktop job 全挂在 `cargo test --locked`：

```
error: unexpected end of input while parsing minor version number
--> desktop/src-tauri/Cargo.toml:3:11  version = "1.1"
```

**修法**：版本号改 `1.1.0`，并同步 `Cargo.lock` / `package.json` / `tauri.conf.json` / Android `versionName` / 产物名。

**经验**：**版本号是「一处改、五处同步」的东西**。这个项目后来把它写成发布清单（每次 release 提交都列出同步了哪几处）。

### 7.3 Windows 编译 macOS 专属 API（`1f5ad6b`）

v0.3.0 发布后 Windows job 编译失败，根因是 `title_bar_style` 是 macOS 专属 API。修法：`#[cfg(target_os = "macos")]` 门控。

**经验**：跨平台代码里的平台专属 API，**编译期门控**而不是运行期判断。

### 7.4 Chaquopy 的 pydantic 1.10（BUG-023，最贵的一个环境坑）

**现象**：v1.3.0 CI 的 desktop 三个 job 全过，**android job 的模拟器 smoke 测试失败**，240s 等不到 `BILIMUSIC_WEB_READY`，dump 出 `BiliMusic: Startup failed`。

**根因**：

```
com.chaquo.python.PyException: ValueError: On field "queue" the following field constraints
are set but not enforced: max_length.
    at <python>.app.api.routes.<module>(routes.py:628)
```

Android 侧 Chaquopy 装的是 **pydantic 1.10.22**，开发 venv 是 **2.x**。`SessionReport.queue: list[dict] = Field(default_factory=list, max_length=200)` 在 v1 上**建模阶段**直接抛错 → `app.api.routes` 导入失败 → 内嵌后端起不来。桌面端与 Web 端都是 pydantic 2，所以本地一切正常。

**修法**：

- `queue` 去掉 `max_length`（上限本来就在 `session_bus` 里按 `MAX_QUEUE` 截断）；
- 设备 id 的 `pattern` 去掉（v1 不认、静默忽略）→ 改在 `session_bus.clean_id()` 里做 `[A-Za-z0-9_-]` 清洗与限长（顺带堵住「设备 id 直接拼进 HTML」的口子），设备名同样去控制字符；
- `body.model_dump()` → `body.model_dump() if hasattr(body, "model_dump") else body.dict()`。

**验证**：本机 AVD BM35 + debug APK 跑 CI 同款步骤：修前 3s 就 `Startup failed`；修后 **36s 出现 `BILIMUSIC_WEB_READY`**。

**教训（原文照抄）**：**Android 侧是 pydantic 1.10——别用 v2-only 写法（`model_dump` / `model_validate` / list 字段上的 `max_length` / `pattern=`）。改后端后先在本机构建 debug APK 跑一次 smoke，比等 CI 快。**

### 7.5 其他打包问题

- **封面/图像取不到**（09-07 用户报「所有构件的客户端都不能正确获取图像」）：打包后 WebView 从 HTTPS 页面加载 HTTP 资源被拦 → 后端代理 B 站媒体并走 HTTPS（`4d7a897`）。

## 8. 数据迁移：改历史数据要像做手术

这个项目有几条**幂等迁移**，都在 `app/db/session.py::_migrate` 或启动流程里：

| 本地音频 → 在线记录 | 老版本下载的音频转成在线记录后删文件 | 只处理确认存在的旧文件 |

**#24（未修）的风险清单**是一个很好的「迁移前先想清楚」模板：

| 风险 | 说明 |
|---|---|

## 10. 事故与教训清单

### 10.1 测试事故（BUG-020 记录里的一次真实误操作）

验证「取消收藏」分支时，脚本自动点了确认框，触发了「多 P 专辑 → 取消整张收藏」流程，**把该专辑本地 60 首连 B 站收藏一起删了**。

**恢复**：用 `POST /api/imports` 重新导入（专辑 id=5，60/60 分 P），曲库行数 277，已收藏 19 首，`fav_folder_id=4013781715` 说明 B 站收藏也已恢复——与本轮开始前的库状态一致。

**顺带发现的体验问题**：合集子作品点「已收藏的星」会走「取消整张专辑」这条重路径，容易误伤；建议改成对子作品只做本地「移出曲库」。

**教训**：**危险路径的验证脚本默认走 dry-run**；真的要打真实删除接口时，先备份库、并且不要让脚本自动点确认框。

### 10.2 教训清单（按重要性）

1. **接口字段的位置要打日志确认**，不要凭直觉（BUG-001 的 `media_count`）。
2. **枚举值不能当度量用**（BUG-006 的音质 id）。
3. **幂等键要写清业务粒度**（BUG-020 的 `bvid` vs `bvid:cid`）。
4. **兜底链路的每一级都要有置信度门槛，并且「不达标要降级」而不是「直接返回」**（BUG-007）。
5. **候选排序的截断位置会决定命中率**（BUG-008：`[:4]` 把真歌名截掉了，命中率 0/33 → 20/33）。
6. **异步系统里，事件与响应是两条通道**——握手成功不代表后续到达的快照都是新的，要带版本号（#27 的 `revision`）。
7. **窗口期（grace window）是解决抢占类竞态的通用手段**（`TAKEOVER_GRACE = 2.5s`）。
8. **性能问题先证伪**（BUG-021：外部方案 5 条里 2 条不成立）。
9. **跨平台依赖要锁版本并进 CI**（BUG-023 的 pydantic 1.10）。
10. **UI 玄学要量化**（毛玻璃、形变、键盘遮挡——都能用 CDP 量出来）。
11. **层叠上下文先看祖先**，再调 z-index（BUG-012）。
12. **迁移要保守**：只在能确证时动手，宁可少收敛也不要误伤（`_shorten_album_child_titles`）。

## 11. 如果重来一次

1. **重大取舍写 ADR**。砍 Smart Transition 这件事只留了一句代码注释——这是这个项目最贵的一笔「隐性债务」。一页文档（背景 / 选项 / 结论 / 代价 / 何时可以重做）就能省掉后来者的困惑。
2. **死代码设定期限**。`app/analysis/` 与 `smartEnabled()` 的短路链保留是为了「可整体回退」，但应该写清「保留到 v2.x，之后删除」。
3. **接口契约先验证再写代码**。BUG-001 / 006 这类问题，如果先写一个「打一次接口、把响应结构 dump 出来」的小脚本，根本不会发生。这个项目后来在大改前确实这么做了（歌词覆盖率实测、share-link 实测），只是早期没形成习惯。
4. **环境矩阵前置**。开发 venv 是 pydantic 2、Android 是 1.10——这种差异应该在第一次做 Android 打包时就写进 CI，而不是等到 v1.3.0 的 CI 炸掉。
5. **危险脚本默认 dry-run**。见 §10.1。
6. **每个「用户原话」都留档**。台账里的转述会丢信息量；「不要 ai 味」「这个串流很不优美」这种口径，才是需求的本体。
