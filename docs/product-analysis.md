## 1. 一句话定位

**把 B 站当曲库的个人音乐播放器：不建曲库、不买版权、不存音频，只做一个「比 B 站 App 更适合听歌」的前端，外加自建的多设备串流。**

反向说明它**不是**什么：

- 不是版权流媒体（没有版权，也不打算有）；
- 不是本地音乐库管理（不做离线、不扫文件夹）；
- 不是 B 站视频下载器（在线流为主，不落盘）；
- 不是多用户平台（按 B 站账号隔离，一个部署基本服务一个人/一家）。

## 2. 用户与场景

| 维度 | 结论 | 来源 |
|---|---|---|
| 目标用户 | 个人 / 小圈子，自己部署，同一局域网多设备 | `frontend-prd.md` §1 |
| 对标 | **YouTube Music（不是 Spotify 的曲库逻辑，是 YT 的「视频即音源」逻辑）** | `frontend-prd.md` §1 |
| 目标 | 「最好用的 B 站音乐播放器」，不是版权曲库替代品 | `frontend-prd.md` §1 |
| 优先端 | 移动优先（手机浏览器 + Android APK），桌面为第二优先 | `frontend-prd.md` §1 |
| 数据主权 | **曲库以 B 站收藏夹为准确数**，本地是镜像 | BUG-004、v0.5.0 |

**三个真实使用场景**（README 与需求记录里能读出的事实）：

1. **在家听歌**：电脑或手机打开，搜 B 站的歌、听、收藏（收藏直接写回 B 站收藏夹）。
2. **手机 → 电脑接力**：手机上听到一半，走到电脑前，声音接着放（v2.0.0 的主线）。
3. **用 B 站收藏夹当歌单**：多年攒下来的收藏夹，直接变成一个能顺序播放、有歌词、有专辑容器的播放器。

## 3. 竞品地图（四类，不是同一维度上的竞争）

| 类别 | 代表 | 曲库来源 | 与本产品的关系 |
|---|---|---|---|
| **① 版权流媒体** | Spotify / Apple Music / YouTube Music / 网易云 / QQ 音乐 / 汽水音乐 | 版权采购 + 自制 | 正面对手（用户会问「为什么不用这个」），但**曲库完全不同** |
| **② B 站官方** | B 站 App 的音频/后台播放、收藏夹 | 同一套 B 站内容 | 最直接的替代品（「我为什么不用 B 站 App 听」） |
| **③ 自建音乐服务** | Navidrome / Jellyfin / Plex / foobar2000 + 本地曲库 | 用户自己的音乐文件 | 同样是「自建」，但前置条件完全不同（要有文件） |
| **④ 第三方壳/工具** | 第三方 YouTube Music 桌面客户端、各类第三方播放器、yt-dlp + 本地播放器 | 抓取/代理 | 形态最接近，但通常是单机、无跨端、无收藏夹语义 |

**BiliMusic 站稳的位置**：① 的曲库不可能有（B 站那些 live/翻唱/无损合集），② 的播放体验不够（B 站 App 是视频应用），③ 需要你有文件，④ 通常不做跨端与账号语义。

## 4. 横向对比

| 维度 | BiliMusic | 版权流媒体（Spotify/YTM 等） | B 站官方 App | 自建本地库（Navidrome 等） |
|---|---|---|---|---|
| 曲库来源 | B 站用户内容（live/翻唱/无损/教程/合集） | 版权曲库 | 同 B 站 | 你自己的文件 |
| 版权合规 | **灰色地带**（不提供内容，只做播放器） | 合法授权 | 合法 | 合法（自己的文件） |
| 成本 | 0（用户自己的机器） | 订阅费 | 免费（有广告/会员） | 0（但要有文件和硬盘） |
| 歌单语义 | **B 站收藏夹 = 真相源**（视频/多P/系列三种形态统一成容器） | 平台歌单/自己建的歌单 | 收藏夹（视频维度） | 自己建歌单 |
| 歌词 | B 站字幕优先 + LRCLIB 补充（约 89%），带置信度校验 | 官方歌词（通常较全） | 视频字幕 | 依赖文件标签/插件 |
| 音质 | 受 B 站接口档位限制（当前实际取到 192K AAC；Hi-Res/杜比未放开） | 高（含无损/空间音频） | 与 B 站 App 相同 | 取决你的文件（可无损） |
| 离线 | **不做**（纯在线流） | 有（会员） | 有缓存 | 本身就是离线 |
| 跨设备播放 | **有**（自建服务端会话 + 局域网自动发现 + 手势切换） | 有（Spotify Connect / YTM 的设备切换） | 无（多设备各播各的） | 一般没有 |
| 推荐/发现 | 弱（搜索 + B 站相关视频搭车采集） | 强（算法推荐是核心能力） | 强（B 站算法） | 无 |
| 多用户 | **无**（按 B 站账号隔离，一个部署服务一个人） | 有（家庭组） | 有（账号） | 有（多用户库） |
| 部署 | 自己跑一个进程（桌面 App / Android 内嵌 / 局域网） | 注册即用 | 装 App 即用 | 自己跑服务器 |
| 移动端系统集成 | 中（Android 有前台服务/通知/线控；**iOS 完全没有**） | 强（原生 App） | 强 | 中 |
| 稳定性风险 | **高**（寄生第三方接口、风控、条款） | 低 | 低 | 低 |

## 5. 优势（说人话 + 为什么成立 + 证据）

### 优势 1：曲库是「不可能被版权覆盖的那部分」

B 站音乐区的价值不在于「有周杰伦」（那部分随时会下架），而在于**版权体系覆盖不到的现场、翻唱、混音、无损合集、教程、修复版**。这些东西在 Spotify / Apple Music 上根本不存在，在 B 站上却是海量的。

而 BiliMusic 做的事情恰好是：**把这部分内容变成可播放、可收藏、有歌词、有专辑结构的音乐**。

### 优势 2：数据主权 + 零运营成本

- 曲库真相源是**你自己的 B 站收藏夹**，不是某个平台的服务器（`BUG-004` / v0.5.0 定调）；
- 不存音频、不买带宽、不建曲库——服务器就是你自己的一台机器；
- 关掉这个项目，你的收藏夹还在 B 站，**没有任何数据被锁在里面**。

这是所有自建方案共同的优点，但 BiliMusic 做得更彻底：**它连曲库都不存**。

### 优势 3：内容形态的语义做对了（这点连 YouTube Music 都做不好）

B 站有三种内容形态，BiliMusic 全部统一成了一套语义：

| B 站侧 | BiliMusic | 难点 |
|---|---|---|
| 单视频 | 一首歌 | —— |
| 多 P 视频 | 一张「专辑」，分 P 是曲目，**逐分 P 星标** | B 站算 1 条收藏，本地算 N 首 |
| 跨视频系列 | 一张「合集」，每个视频是一条曲目 | 每个视频各收藏一次 |

YouTube Music 处理「视频即音源」时最被诟病的就是这个映射（一个视频/一张专辑/一个播放列表到底算什么）。BiliMusic 把它显式建模成 `Album.kind = paged | series`，并且**收藏/删除/同步三处语义都跟着 kind 走**。

### 优势 4：跨端串流是自建方案里少见的

自建音乐服务里，能像 Spotify Connect 一样「多设备共享一份播放会话、点一下就换设备继续放」的极少。而 BiliMusic 的实现有一个漂亮的架构结论：

> **跨端接力转移的是「会话状态」，不是音频数据**——接收端自己向后端取流并 seek 到目标位置。

带来的好处：不需要任何音频投送、不需要 P2P、不需要 WebRTC；实现就是「服务端权威会话 + SSE + 客户端 seek + 交叉淡入掩盖缝隙」。局域网内零配置（固定端口扫描自动发现），手机上用手势（上拖选设备/下拖回本机），桌面上点设备图标。

用户对最终形态的评价原话是：「**可以。我很满意。**」

### 优势 5：歌词的多源策略是对的

不是「谁先给用谁」，而是**B 站字幕优先（与视频绑定、不可能错配）+ LRCLIB 补充（覆盖高但要过置信度校验）+ 网易云默认关闭（错配率高）**。实测覆盖率 72.5% → 89.2%，且明确记录「宁缺毋滥」（教程类视频没歌词是符合预期的）。

### 优势 6：轻到可以塞进任何壳里

- 后端 FastAPI 单进程 + SQLite；
- 前端**服务端渲染 + htmx + 原生 JS，零构建**（`frontend-prd.md` 明确写「不引入构建链是现状，不是约束」）；
- 因此同一套代码能跑在浏览器、Tauri 桌面壳（系统 WebView）、Android WebView（Chaquopy 内嵌 Python）三种容器里。

对一个个人项目来说，「没有构建链」= 没有半年后升级依赖的地狱。

## 6. 不足与结构性风险（诚实版）

### 风险 1：完全寄生在第三方上（最根本的一条）

- 接口会变（本项目已经被 `media_count` 的字段位置坑过一次）；
- 风控会变（系列拉取必须严格限速，`seasons_archives_list` 可能限流）；
- 条款会变（B 站没有任何义务让这个客户端继续工作）；
- 音质档位受会员与接口参数限制（当前 `fnval=16`，只拿到基础 DASH）。

**这不是可以修好的 bug，是这类产品的固有属性。** 唯一能做的缓解是：失败降级、频控、以及把接口层收在一个模块里（`app/bili/`）方便改。

### 风险 2：登录链路天然脆弱

扫码要用户手动确认、短信要过极验、WebView 里的验证码兼容性是个无底洞。项目最后选择「二维码存相册 + 拉起 B 站 App」这个变通——能用，但**不优雅**，而且依赖 B 站 App 的相册扫码入口存在。

### 风险 3：没有离线、没有自带曲库 = 完全依赖网络

断网、B 站 CDN 抽风、视频被删，都会直接反映为「播不了」。这不只是体验问题：**它意味着这个播放器无法成为你唯一的音乐来源**。

### 风险 4：单账号、无多用户

按 B 站账号隔离（`account_scope(mid)`），没有「家庭共享」的概念。想给家人用就得各自部署或共享一个账号。

### 风险 5：局域网限定

跨网络（手机 4G 连家里）不在范围，官方建议挂 Tailscale。这是一个**很务实的取舍**（见 §7），但确实挡住了「在外面也能听」的核心诉求。

### 风险 6：移动端系统集成仍然弱

Android 有前台服务 + MediaSession（通知栏、锁屏、线控、耳机拔出暂停），但：

- iOS 完全没有客户端；
- Android 的后台播放依赖前台服务与 WakeLock/WifiLock（BUG-021 就是这里出的问题）；
- 浏览器标签页关掉就停播。

### 风险 7：内容发现是短板

没有推荐算法，也没有「每日推荐」。现有的推荐是「播放起播后搭车采集相关视频元数据」，本质是 B 站推荐结果的二次利用。跟版权流媒体的算法推荐不在一个量级。

### 风险 8：可维护性依赖一个人 + 一套文档

无构建链降低了技术债，但也意味着：前端是手写的 7000 行 JS/CSS，没有类型检查、没有组件框架、没有设计系统。规模再大一个量级就会开始疼。

## 7. 取舍分析（每条：选项 → 选了什么 → 放弃了什么 → 值不值）

### 取舍 1：纯在线流式 vs 离线下载

- **放弃**：Smart Transition（本地音频分析 + 双轨交叉淡化）整套能力、离线听歌、无损以外的高音质可能。
- **换来**：不占磁盘、导入即听、多设备零成本、绕开本地文件的盗链与时效问题。
- **评价**：**做对了**。智能过渡是一个技术很酷但需求很弱的功能（用户从来没人要求过「过渡更顺滑」），而「手机电脑接着放」是真实高频诉求。
- **代价管理得不好**：`app/analysis/` 与 `smartEnabled()` 保留至今，没有期限。应该写 ADR + 设定期限。

### 取舍 2：B 站收藏夹为真相源 vs 本地独立曲库

- **放弃**：用户可以在 App 里建一个「不污染 B 站收藏夹」的私有库。
- **换来**：**零迁移成本**（换设备、换浏览器、重装，收藏夹就是曲库）、与 B 站行为一致（在 B 站 App 收藏的歌，这边自动有）。
- **评价**：**做对了**。这是这个产品最聪明的定位——它放弃了「做一个曲库」的野心，只做「一个更好的播放前端」，于是不用承担任何数据托管责任。
- **代价**：所有删除/收藏操作都要在 B 站侧找到语义（不能一键删本地），否则就会出现 BUG-004 那种计数不一致。

### 取舍 3：服务端权威会话 vs 端对端

- **放弃**：不依赖服务器的 P2P 方案。
- **换来**：实现简单得多（`SessionBus` 单例 + SSE + HTTP 命令通道），且天然支持「三台以上设备」。
- **评价**：**做对了**。前提是「本来就要指向同一个后端」，所以在架构上没有增加新的依赖。
- **代价**：**这个前提在 Android 上没落地**——手机固定连自己的内嵌后端（#26 的根因），后来不得不加一整套局域网发现来补。

### 取舍 4：固定端口扫描 vs mDNS vs 手输地址 vs 扫码

| 方案 | 评价 |
|---|---|
| 手输 IP | 最省事，但「自动、无感」是用户的明确要求（原话） |
| mDNS | 体验最好，但要给桌面壳加依赖、动打包，2~3 天 |
| **固定端口扫描** | **选了它**：零新依赖、全自动；代价是只覆盖 /24 网段（家庭网络足够） |
| 扫码配对 | 链路最长（要动原生 WebView 扫码入口） |

- **评价**：**做对了**。「约定一个端口，扫这个网段」是个很聪明的工程折中——用户不需要知道 IP，代码不需要新依赖。
- **代价**：如果路由器隔离客户端（AP isolation）或者用 /16 之类的大网段，就不能发现。README 里如实写了。

### 取舍 5：无构建（SSR + htmx + 原生 JS） vs 现代前端框架

- **放弃**：组件化、类型检查、生态（Tailwind/shadcn 那套）。
- **换来**：三种容器（浏览器/Tauri/Android WebView）零适配成本；没有 node_modules；改完刷新就能看。
- **评价**：**在「一个人 + 8 天出 10 个版本」这个语境下做对了**。但这是**现状不是约束**（PRD 原话），规模再大一档就得重新评估。

### 取舍 6：播放条即遥控 vs 独立设备页

- 用户第一版做的是「设备整页」，评价是「很不优雅，不要了」；最终的答案是**把能力降级成播放条的一个状态 + 一个手势**（手机长按/上拖，桌面点设备图标）。
- **评价**：**做对了**，而且这是一条通用的产品经验——**功能做对了但入口做错了，看起来就像功能错了**。

### 取舍 7：「串流零提示」 vs 明确反馈

- 用户两次明确要求：「串流的时候不要提示」「我不想要串流的任何提示」。
- 实现上：成功与进度提示全删，**只保留失败类**（设备未响应 / 没有可搬运的会话 / 接管失败 / 浏览器拦了自动播放）。
- **评价**：**做对了**。切换的结果由播放条呈现（镜像 + 粉色光晕），比 toast 更不容易错过。这条也被写进了 e2e 断言（`toastLog = []`），成了可回归的产品契约。

### 取舍 8：不做采样级相位对齐

- 用户拍板：「几百毫秒相位差够了，用户体验差不多的」。
- **放弃**：两端音频完全同步（做起来要处理时钟漂移、缓冲对齐，成本远高于收益）。
- **换来**：用 350ms 交叉淡入把缝隙掩盖掉，听感上「连续」即可。
- **评价**：**做对了**。这是很成熟的取舍——**明确一个体验的验收口径（「听不出来」），而不是追求技术指标的完美**。

### 取舍 9：单账号 vs 多用户

- **放弃**：家庭共享、多租户。
- **换来**：账号模型极简（一个 mid 一个目录）。
- **评价**：对个人项目合理。真要做多用户，鉴权、配额、数据隔离的成本会翻几倍。

### 取舍 10：局域网 vs 公网

- **放弃**：在外面也能听。
- **换来**：不用做用户体系、不用做鉴权加固、不用担心把带 cookie 的后端暴露到公网。
- **评价**：合理，但**这决定了它只是一个「家里的播放器」**。README 给的缓解方案是 Tailscale（两端组网后按局域网使用）。

## 8. 如果继续做：按 ROI 排序的建议

| 优先级 | 事项 | 理由 |
|---|---|---|
| P0 | **音质放开 + 修 BUG-006** | 现在实际只有 192K；`max(quality_id)` 的选档逻辑一旦放开高音质就会选错。这是「用户能直接听出差别」的功能 |
| P0 | **真机验收 backlog 清零**（#24 / #28 / Android 打包复验） | 台账里躺着的都是真机实测出来的问题 |
| P1 | **离线缓存（只缓存听过的）** | 明确「不做下载器」，但可以做「听过的可以离线」——解决通勤场景 |
| P1 | **移动端后台播放补强**（现在的 WakeLock 方案够用但脆） | 通勤场景的关键 |
| P1 | **内容发现**：UP 订阅 / 收藏夹更新提醒 / 简单的新歌清单 | 现在全靠用户自己搜索 |
| P2 | **多用户 / 家庭共享** | 需要重构账号模型，成本高 |
| P2 | **iOS 客户端** | 只有 PWA 级别的体验 |
| P2 | **广域网访问**（把 Tailscale 做成内置引导） | 从「家里的播放器」变成「随身播放器」 |
| P3 | **歌词质量看板**（哪首歌没歌词、为什么） | 现在的兜底是「取不到就标记不再请求」，用户看不到原因 |
| P3 | **把 Smart Transition 的坟头立好**（ADR + 删除死代码，或者重新设计成在线可用） | 见技术复盘 §11 |

## 9. 结论

**它适合谁**：

- 你本来就在 B 站听歌（收藏夹里攒了一堆 live/翻唱/无损合集）；
- 你家里有不止一台设备，想「走到哪放到哪」；
- 你愿意自己跑一个进程，并且能接受「它随时可能因为 B 站改接口而坏掉」；
- 你不指望它替代 Spotify——你只是想要一个**更顺手的 B 站播放器**。

**它不适合谁**：

- 想要一个稳定、有版权、有推荐的日常音乐 App；
- 需要离线听歌；
- 需要多用户/家庭共享；
- 不懂也不想碰命令行与自部署。

**一句话总结**：BiliMusic 的产品判断是**「不做曲库，只做播放前端」**——它把最大的风险（版权与托管）留给了别人，把最大的价值（B 站独有的内容 + 数据主权 + 跨端体验）留给了自己。这个取舍在个人自用场景下是成立的；它所有的不足，几乎都能追溯到「它寄生于一个不承诺稳定性的第三方」这一条根因上。**这不是能被修好的缺点，而是被明确接受的设计前提。**
